# ADR-003: 화면 캡처 구현 방식

- 상태: 제안됨
- 날짜: 2026-07-14
- 관련 문서: docs/07_CAPTURE_AND_UPLOAD_SPEC.md, docs/11_QA_SECURITY_RELEASE.md §1

## 배경

화면 영역 캡처는 이번 주 핵심 기능이지만 접근법이 백지 상태다. Tauri는 "영역 선택 오버레이 + 픽셀 캡처"를 기본 제공하지 않으므로, 픽셀 획득과 영역 선택 UI를 각각 설계해야 한다. 다중 모니터와 DPI 배율 좌표 변환이 실제 난도의 대부분을 차지한다.

제약:

- 흐름: 메인 창 숨김 → 오버레이 → 드래그 선택 → Escape 취소 → PNG 임시 저장 → 앱 복귀(docs/07 §3).
- 취소는 오류가 아니라 정상 사용자 행동으로 처리(docs/07 §6).
- Windows 다중 DPI/배율, macOS 화면 기록 권한/Retina 고려(docs/07 §4, §12).
- 임시 파일은 앱 전용 temp에만 저장(docs/07 §11).

## 선택지

### A. 순수 Rust 크레이트로 픽셀 획득 + Tauri 투명 오버레이 창으로 영역 선택 (권장)

- 픽셀 획득: `xcap`(크로스플랫폼 스크린/윈도우 캡처) 또는 `screenshots` 크레이트.
- 영역 선택: 메인 창을 숨기고, 각 모니터를 덮는 풀스크린 투명·프레임리스 always-on-top Tauri 창을 띄워 웹뷰(Canvas/DOM)로 드래그 사각형을 그린다. 선택 좌표를 물리 픽셀로 변환해 Rust에 전달, 해당 영역만 크롭 후 PNG 저장.
- 장점: 선택 UI를 웹 기술로 구현해 브랜드/접근성(Escape 안내 등) 일관. 크레이트가 크로스플랫폼.
- 단점: 다중 모니터·DPI 좌표 변환을 직접 처리. 오버레이 창 show/hide와 메인 창 숨김의 타이밍 레이스 주의.

### B. OS 네이티브 캡처 UI 호출

- Windows `ms-screenclip:` 또는 macOS `screencapture -i`를 호출.
- 장점: 좌표 변환/오버레이를 OS에 위임.
- 단점: 결과 반환/취소 감지가 OS별로 제각각이고 통합 어려움. 앱 브랜드/흐름 통제 불가. macOS는 파일 경로 회수, Windows는 클립보드 경유 등 파편화. MVP 계약(`capture_region` 단일 command)과 맞추기 번거로움.

### C. 브라우저 `getDisplayMedia`(화면 공유 API)

- 장점: 웹 표준.
- 단점: 권한 프롬프트가 화면 공유 UX라 "영역 캡처"와 어긋남. 프레임 캡처는 되지만 영역 드래그 선택엔 부적합. 데스크톱 네이티브 기대와 불일치.

## 결정

**A**를 권장한다. 픽셀 획득은 `xcap`을 1순위 후보로 프로토타입한다.

근거:

- 캡처 흐름 전체(오버레이, Escape 취소, 미리보기)를 앱이 통제해야 브랜드/접근성 요구를 만족한다.
- 단일 `capture_region` command 계약(docs/07 §6)과 자연스럽게 맞는다.

## 결과

- **Day 4 전 스파이크 필수**: 단일 모니터에서 `xcap` 캡처 + 투명 오버레이 드래그 선택 + PNG 저장을 먼저 검증한다. 여기서 크레이트/좌표 변환 리스크를 조기에 확인한다.
- 이번 주 목표는 **단일 모니터 안정 동작**. 다중 모니터/고배율은 테스트 매트릭스(docs/07 §12)로 확인하되, 불안정하면 UI에 명시하고 후속 범위로 둔다.
- command 계약: `invoke<CaptureRegionResult>("capture_region")`, 오류 코드 `CANCELLED|PERMISSION_DENIED|CAPTURE_FAILED|SAVE_FAILED|UNSUPPORTED`. `CANCELLED`는 toast가 아닌 정상 복귀로 처리.
- 임시 파일 경로 `{appTemp}/captures/{uuid}.png`, 취소 시 즉시 삭제, 앱 시작 시 오래된 파일 정리(docs/07 §11).
- macOS 화면 기록 권한 거부 시 시스템 설정 안내 화면을 제공(docs/07 §4).
- 재검토 조건: `xcap`가 특정 OS/보호 화면에서 검은 화면을 반환하면 대체 크레이트 또는 OS API 폴백을 별도 ADR로.

## 구현 정정 (2026-07-28, ADR-008)

선택지 A는 영역 선택을 "별도의 투명·프레임리스 always-on-top 창"으로 적었으나, 실제 구현은 **메인 창을 전체화면으로 전환한 라우트**(`/app/capture`)다. 별도 창을 만들지 않는다.

이유는 ADR-008과 같다 — Tauri `WebviewWindow`마다 JS 컨텍스트가 분리되어 별도 창은 인증·스토어·Query 캐시를 공유하지 못한다. 프리즈 프레임과 선택 좌표를 그대로 다음 단계로 넘기려면 같은 컨텍스트여야 한다.

전체화면 전환은 `set_window_mode`의 `overlay` 모드가 담당하며, 라우트에서 파생되므로 페이지가 창을 직접 만지지 않는다. `xcap` 픽셀 획득과 좌표 변환에 대한 위 결정은 그대로 유효하다.
