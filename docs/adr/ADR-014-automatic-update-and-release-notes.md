# ADR-014: 자동 다운로드, 다음 실행 시 설치, 변경 내역

- 상태: 구현 및 격리된 서명 QA 앱의 Windows/macOS A→B 설치 검증 완료
- 날짜: 2026-10-20
- 대체: ADR-011의 수동 설치 UI 정책. 기존 GitHub Releases와 업데이터 키는 유지한다.

## 사용자 흐름

앱 실행과 이후 6시간 간격으로 새 버전을 확인한다. 포커스 복귀·네트워크 복구에서도
확인 시각을 검사한다. 다운로드 실패 후 재시도 간격은 최소 15분이며 수동 확인은
즉시 가능하다. 실행 중에는 자동으로 설치하거나 재시작하지 않는다.

다운로드가 끝나면 다음 실행에서 앱 화면·캡처 단축키를 마운트하기 전에 설치한다.
설치 직전 현재 피드(요청 제한 5초)를 다시 확인해 철회되거나 교체된 패키지를 적용하지
않는다. 오프라인이면 기존 앱으로 진입하고 다운로드 파일을 보관한다.
다운로드 자체의 제한 시간은 5분이다.

설정의 **지금 업데이트**는 진행 중인 캡처·분석·보정·저장·입력 처리 및 미저장 입력/
선택을 검사한다. 저장 후에도 선택을 바꿀 수 있으므로, **새 장면**으로 작업을 종료하기
전에는 설치를 보류한다. 누른 직후에도 같은 상태를 다시 확인한다. 설치 중에는 앱 화면을
마운트하지 않아 새 작업을 시작할 수 없다. Windows는 설치 호출에서 프로세스가
종료될 수 있고, macOS는 설치 완료 후 명시적으로 재시작한다.

## 네이티브 저장과 복구

Rust가 Update 핸들과 작업 잠금을 소유한다. 앱별 local data 디렉터리의 `updates-v1`
아래 `package.bin`, `pending.json`을 보관한다. 다운로드 때 Tauri 플러그인이 minisign
서명을 검증하며, 설치 때 파일을 다시 읽고 내장 공개키로 재검증한다.

각 파일은 임시 파일 쓰기→sync→rename으로 저장한다. 패키지를 먼저 저장하고
메타데이터를 마지막에 공개한다. 중간 종료, 손상된 메타데이터, 누락된 파일, 이미
실행 중인 버전 이하의 캐시는 설치 대상으로 삼지 않는다. 파일 경로를 IPC 입력으로
받지 않는다.

실제 설치/검증 시도 직전에 `attempted=true`를 디스크에 쓴다. 같은 버전의 자동
설치는 한 번만 시도하며, 이후에는 설정에서 직접 재시도한다. 같은 업데이트를 다시
확인해도 시도 기록을 초기화하지 않는다. 손상된 패키지는 수동/주기적 확인에서 다시
다운로드할 수 있다. 실제 새 바이너리 버전을 확인했을 때만 기존 `update_installed`
이벤트를 기록한다. 기존 분석 동의 정책을 따른다.

## 변경 내역

`releases/notes.json`이 유일한 원본이다. 버전은 SemVer 오름차순이며 각 항목은
version/date/title/features/improvements/fixes를 갖는다. 이력을 삭제하지 않는다.
원본은 앱 번들에 포함되므로 변경 내역 팝업에는 네트워크가 필요 없다.

첫 도입/최초 설치는 현재 버전 소개를 보여준다. 이후에는 마지막 확인 버전보다 새롭고
현재 실행 버전 이하인 모든 변경을 한 팝업에 모은다. 닫기/확인을 누르면 Rust가 앱별
local data의 `release-notes-v1/seen-version`에 실제 실행 버전을 sync→rename으로
저장한다. 저장이 끝난 뒤에만 팝업을 닫고, 실패하면 팝업에서 재시도할 수 있다.
`standin.updates.lastSeenRelease`는 웹 미리보기·기존 기록 호환용 캐시이며 데스크톱은
네이티브 기록을 우선한다. WebKit이 localStorage를 디스크에 쓰기 전에 앱을 종료해도
확인 기록을 잃지 않는다. 설정에서는 다시 열 수 있고 로그인과 독립적이며 다운그레이드로
확인 버전을 낮추지 않는다.

자동 팝업은 앱 모드의 홈/설정에서만 표시한다. 작업·온보딩·투어·다른 모달이 끝날
때까지 대기한다. 플로팅 바/캡처 화면에서 강제로 앱 모드로 전환하지 않는다.

## 릴리스 절차

1. 새 버전을 `node scripts/set-version.mjs <version>`으로 지정한다. package/lock,
   Tauri config, Cargo manifest/lock을 함께 갱신한다.
2. `releases/notes.json`에 실제 사용자 변경을 추가한다. `npm run release:check`는
   버전 불일치, 빈 내역, placeholder, 중복/역순 버전을 거부한다.
3. 릴리스 워크플로는 같은 원본으로 GitHub 설명을 생성한다. 공개된 버전은 덮어쓰지
   않으며 Windows/macOS를 항상 draft로 빌드한다.
   macOS는 최종 앱에 공증 티켓을 부착한 뒤 updater 아카이브를 다시 만들고,
   압축을 풀어 코드서명·티켓을 확인한 후 updater 서명을 생성한다.
   초기 설치용 DMG도 검증된 앱으로 재구성·재서명하고 내부 앱의 티켓을 확인한다.
4. 두 플랫폼의 서명 검증이 통과하면 finalize가 `latest.json`의 버전과 세 플랫폼
   항목을 검증하고 notes를 같은 원본으로 갱신한다.
5. 기본 `draft=true`는 검증된 초안으로 남긴다. `draft=false`일 때만 finalize가
   공개한다. 서명/공증 자격증명이 없는 production 빌드는 공개할 수 없다.

dev와 staging의 빈 endpoints, 별도 앱 identifier, staging prerelease 정책은 유지한다.
실기 업데이트 검증은 production 피드를 쓰지 않는 별도 identifier와 HTTPS 테스트
피드를 가진 서명된 A/B 빌드로 한다. production용 minisign 개인키를 테스트에 복사하지
않고 별도 테스트 키쌍을 사용한다.

기존 사용자에게 이 기능이 포함된 첫 버전은 기존 방식으로 한 번 설치해야 한다.
새 서버 API, 강제 업데이트, 단계적 배포, 무인 다운그레이드는 이번 범위에 없다.

## 배포 전 실기 확인

[2026-10-20 검증 결과](../qa/2026-10-20-signed-updater.md): Windows x64와 macOS
Apple Silicon·Intel에서 7개씩 21개 시나리오를 통과했다. 아래 전체 배포 점검 목록과
실제로 수행한 E2E 범위는 검증 보고서에서 구분한다.

[후속 Universal 검증](../qa/2026-10-20-universal-updater.md)에서는 두 Mac CPU 모두
Universal DMG의 A→B 업데이트와 추가 시작 검사를 통과했다.
DMG 재구성용 볼륨에 Universal 실행 파일을 교체할 공간을 확보하도록 수정했다.
원본 바이너리 조사를 포함한 시작 300회에서 과거 시간 초과는 재현되지 않았으나,
근본 원인을 확정한 것은 아니다.

- Windows NSIS, macOS Apple Silicon/Intel: A에서 B 다운로드→종료→다음 실행 설치→재실행.
- 다운로드 도중 종료/네트워크 단절, 다운로드 후 오프라인 실행, 파일 변조·디스크 오류.
- 설치 권한 거부/설치 실패 후 기존 버전 실행, 자동 설치 반복 방지와 수동 재시도.
- 새 작업이 설치 대기/설치 도중 시작되지 않는지, 캡처·분석·보정·저장 중 차단.
- 최초 소개, 여러 버전 건너뛰기, 확인 후 재실행, 설정 다시 보기, 바/투어 표시 보류.
- production과 staging 상호 업데이트가 일어나지 않는지.
