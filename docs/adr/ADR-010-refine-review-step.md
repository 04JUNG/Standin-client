# ADR-010: 저장 전 조정 결과 확인 단계

- 상태: 제안됨
- 날짜: 2026-08-05
- 관련 문서: ADR-005(3D 뷰어 도입 시점), ADR-009(포즈 파일 전달), `docs/12_EXPORT_AND_SAVE_SPEC.md`,
  `Standin-server/docs/PR10_MAIN_MERGE_REQUIREMENTS.md` FE-04

## 배경

추론 서버가 refine을 제공하면서, 작가가 후보 카드에서 고른 포즈와 **실제로 저장되는 포즈가
달라질 수 있게** 되었다. refine은 유효한 사지만 러프에 맞춰 조정하고 안전하지 않으면 베이스를
유지하므로 결과는 "좋아지거나 그대로"지만, 어느 쪽이든 저장 전에 확인할 수단이 없다.

두 제약이 충돌한다.

- ADR-009: 저장 화면은 **진입 즉시 자동 저장**한다. 폴더·파일명을 확인하고 저장 버튼을 누르는
  단계가 마찰의 대부분이었기 때문에 없앴다.
- FE-04: 사용자가 선택한 포즈와 저장되는 포즈가 다를 수 있으므로 **저장 전에** 조정 결과를
  확인할 수 있어야 한다.

또한 현재 후보 화면은 정적 thumbnail만 보여준다. 조정본은 thumbnail이 없으므로(라이브러리
포즈가 아니라 그 자리에서 만들어진 BVH다) 확인하려면 BVH 자체를 그려야 한다.

## 선택지

1. **저장 화면에 저장 버튼을 되살린다.** FE-04는 충족하지만 ADR-009가 없앤 마찰이 그대로 돌아온다.
2. **저장 후에 결과를 보여준다.** 자동 저장은 지키지만 "저장 전 확인"이 아니다. 마음에 들지 않으면
   이미 쓴 파일을 지워야 한다.
3. **확인 전용 화면을 저장 앞에 둔다.** 후보 확정 → 확인 → 저장. 저장 화면은 손대지 않는다.
4. **refine을 비활성화한다.** 요구서가 허용하는 선택지(FE-04)지만 이번 통합의 목표를 포기한다.

## 결정

**3안.** `/app/jobs/:jobId/review`와 `/bar/review`를 추가한다.

- 확인 화면이 refine을 호출하고(`useRefineSelection`), 조정이 도는 동안 진행 상태를 알린다.
- 무엇이 저장되는지 인물·후보 목록으로 보여준다.
- 저장 화면(`SavePage`/`BarSavePage`)의 자동 저장은 그대로 둔다. ADR-009는 유효하다.

### 개정 (2026-08-05) — 3D 미리보기 철회

처음에는 확정된 export URL의 BVH를 three.js로 그려 실제 저장 대상을 보여주려 했다
(`BvhPreview`). **실제로 띄워 보니 자세가 반영되지 않고 기본 T자 뼈대가 나왔다.**

`BVHLoader`가 만든 뼈대가 HIERARCHY의 OFFSET만 반영한 rest pose라는 것까지는 확인해
`AnimationMixer`로 첫 프레임을 샘플링하도록 고쳤지만, 그것만으로는 실제 화면에서 자세가
나오지 않았다. 원인이 규명되지 않은 상태에서 뷰어를 남기면 **작가에게 저장될 포즈라며 틀린
자세를 보여주게 된다.** CLAUDE.md §10("구현하지 않은 기능을 작동하는 것처럼 보이게 하지
않는다")에 정면으로 어긋난다. 확인 수단이 없는 것보다 나쁘다.

그래서 `BvhPreview`·`LazyBvhPreview`와 three 의존성을 제거했다. 조정 여부를 알리던 배지
(`RefineBadge`)도 함께 뺐다 — 무엇이 달라졌는지 볼 수 없는 상태에서 "러프에 맞춰 조정됨"만
알리면 근거 없는 안심을 준다.

결과적으로 이 화면은 **저장 전 진행 상태 게이트**이지 시각적 확인 수단이 아니다. FE-04의
"저장 전 조정 결과 확인"은 아직 충족되지 않았다. refine을 production에서 켜기 전에 둘 중
하나를 해야 한다.

- 실제 자세가 나오는 미리보기를 다시 만든다 (T자 원인 규명이 선행)
- 미리보기 없이 refine을 켜지 않는다 (요구서 FE-04가 허용하는 선택지)

3D 뷰어 도입 시점(ADR-005)은 **미결로 되돌아간다.**

### 개정 2 (2026-09-04) — 서버 렌더 미리보기로 FE-04 충족

위 두 선택지 중 어느 쪽도 고르지 않고 **세 번째**를 택했다. 클라이언트가 BVH를 그리는 대신
추론 서버가 후보 썸네일과 같은 렌더러로 최종 결과를 한 장 더 그려 준다
(`docs/REFINED_PREVIEW_REQUEST.md` → Standin-server `feat(refine): return front thumbnail
preview`). T자 원인을 규명하지 않아도 되고, 클라이언트 번들도 늘지 않는다.

그림 하나를 더 그리는 것으로 철회 사유 둘이 같이 사라진다.

- **시각 언어가 같다.** 후보 카드와 확인 화면이 같은 렌더러(`warm-mannequin-v1`)·같은
  `view`의 그림이다. 같은 포즈를 렌더 캐릭터와 막대 스켈레톤 두 가지로 그리지 않는다.
- **저장될 것을 그린다.** `refined=true`면 조정본 BVH를, `false`면 실제로 저장될 베이스
  BVH를 렌더한다. 클라이언트가 "저장될 것과 비슷한 것"을 그리는 상태가 아니다.

BFF는 받은 PNG를 조정본 BVH와 같은 S3 prefix에 보관한다. 멱등 캐시가 추론 재호출을 막으므로
보관하지 않으면 작업 기록 재진입(ADR-012)에서 그림이 사라진다.

조정 여부 배지(`RefineBadge`)도 되살렸다. 철회 당시 뺀 이유는 "무엇이 달라졌는지 볼 수 없는
상태에서 조정됐다고만 알리면 근거 없는 안심을 준다"였는데, 이제 결과를 볼 수 있으므로 그 근거가
없어졌다. 오히려 배지가 없으면 후보와 미묘하게 다른 그림이 오류로 읽힌다.

**그림이 없는 것은 오류가 아니다.** 서버가 렌더하지 못했거나 refine을 아예 건너뛴 인물은 고른
후보의 썸네일로 폴백한다 — 그 경우 실제로 저장되는 것도 그 후보의 베이스 포즈다.

FE-04는 이것으로 충족된다. 3D 뷰어 도입 시점(ADR-005)은 여전히 미결이다 — 이 화면이 요구하는
것은 정지 이미지 한 장이지 뷰어가 아니다.

## 결과

- 후보 확정에서 저장까지 화면이 하나 늘어난다. 확인 후 버튼 한 번이므로 마찰은 클릭 1회다.
- 앱과 바가 `useSelectionReview` / `useRefineSelection`을 공유한다. 표면마다 저장 결과가
  달라지면 안 된다.
- `modeRoutes`에 review 단계를 추가해 앱↔바 왕복이 같은 단계로 돌아온다.
- `barSizes`에도 review 단계를 추가한다. 빠뜨리면 `barStateForPath`가 null을 돌려주고
  창이 앱 모드(1280×800)로 커진다 — 바에서 확인 화면에 들어가는 순간 플로팅 바가 사라진다.
- 추가 의존성은 없다. three는 미리보기 철회와 함께 제거했고, 서버 렌더 미리보기는 PNG 한 장이라
  다시 필요해지지 않았다.
- **재검토 조건**: refine을 production에서 끄기로 확정하면 이 화면은 조정본이 없는 선택만
  보여주게 되므로, 그때는 확인 단계를 건너뛸지 다시 판단한다.
