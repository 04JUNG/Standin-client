# 포즈 후보 뷰어 및 저장·전달 명세

## 1. 목표

- 포즈 후보 5개를 비교하고 마음에 드는 후보를 선택하는 뷰어 구현
- 후보를 고르면 **설정된 저장 폴더에 대화상자 없이 바로 저장**
- 저장된 BVH를 **클립스튜디오 캔버스로 드래그 앤 드롭**해 포즈를 적용
- 저장 폴더는 설정 화면에서 변경하고, 저장 시점에 이번 한 번만 다른 폴더를 고르는 부가 경로도 제공

전달 방식의 결정 근거는 `docs/adr/ADR-009-pose-file-delivery.md`에 있다. 클립스튜디오 소재 폴더 직접 저장과 소재 DB 조작은 조사 결과 성립하지 않아 **영구 제외**한다(§5, §6).

---

## 2. 포즈 후보 뷰어

`docs/01_PRODUCT_AND_MVP.md` §5의 후보 뷰어 요구사항을 따른다.

- 포즈 후보 5개를 나란히 표시
- 후보별 썸네일과 `matchLevel`(`high` / `medium` / `low`) 표시
- 카드 클릭 시 선택 상태로 전환, 선택된 카드는 확대 비교 가능
- 후보 선택은 서버 상태와 분리해 관리한다(`PoseSelectionState`, `docs/09_STATE_AND_DATA_MODEL.md` §4)
- 자동 확정 없음: 하나를 사용자가 직접 선택해야 다음 단계로 진행

타입은 `docs/09_STATE_AND_DATA_MODEL.md`의 `PoseCandidate`, `AnalysisResult`를 그대로 사용한다.

## 3. 전달 흐름

```text
후보 선택
→ 저장할 포즈 확인 (조정 결과 3D 미리보기, ADR-010)
→ 설정된 저장 폴더에 자동 저장 (대화상자 없음, 저장 버튼 반복 없음)
→ 저장 결과에 파일 목록 표시. 목록의 각 행이 드래그 소스다
→ 행을 클립스튜디오 캔버스로 끌어놓음
→ 3D 데생 인형이 자동 생성되고 포즈가 적용됨
```

앱에서 바로 끌어놓으므로 탐색기를 거치지 않는다. 특히 바 모드는 클립스튜디오 위에 떠 있어서 드래그 거리가 가장 짧다.

### 확인 단계에서 무엇을 확인하는가

추론 서버가 선택한 후보를 러프에 맞춰 조정(refine)할 수 있으므로, 작가가 후보 카드에서 고른
포즈와 실제로 저장되는 포즈가 달라질 수 있다. 조정본에는 라이브러리 thumbnail이 없어 정적
이미지로는 확인할 방법이 없다 — 그래서 확인 화면이 BVH를 직접 3D로 그린다.

- 적용됨: "러프에 맞춰 조정됨"
- 안전 게이트가 베이스를 유지: "안전하게 원본 포즈를 유지했습니다"
- refine을 시도하지 않은 선택(저신뢰 인물·서버 flag off): 배지 없음

미리보기는 **저장이 내려받는 것과 같은 URL**을 읽는다. 미리보기 로드 실패는 저장을 막지 않는다.

저장 대상 URL은 BFF가 정한다. 조정 결과가 있으면 그 `exportUrl`을, 없으면 후보의 기존
`bvhUrl`을 쓴다. 앱은 추론 서버의 `/refined/{handle}`를 직접 내려받거나 보관하지 않는다 —
그 파일은 추론 태스크의 로컬 디스크에 있어 태스크가 교체되면 사라진다.

**조정본도 원본과 HIERARCHY·채널 순서가 같다.** 따라서 아래 CSP 축 보정과 드래그 구현은
refine 도입으로 바뀌지 않는다.

### 확인된 동작

검증은 두 축으로 나뉜다. **어떤 포맷을 CSP가 받는가**와 **드래그가 어디서 출발할 수 있는가**다.

| 확인 | 결과 |
|---|---|
| 탐색기 → CSP, BVH 드롭 | 동작. 데생 인형이 **자동 생성**된다 |
| 앱 창 → CSP, BVH 드롭 | **동작**. 이 문서가 정의하는 주 경로 |
| 앱 창 → CSP, PNG·OBJ 드롭 | 동작(이미지·3D 레이어 생성). 드래그 메커니즘 자체를 먼저 가른 대조군 |
| 드래그 후 원본 보존 | **원본이 폴더에 그대로 남는다.** `mode: "copy"` 확인 |

- BVH 드롭 시 캔버스에 인형을 미리 놓거나 선택해둘 필요가 없다.
- 전제: BVH 임포트는 **CSP Ver 3.1 이상**이 필요하다.
- BVH 파일 자체가 유효해야 한다. 형식이 아닌 파일을 넘기면 CSP가 "모션 파일 가져오기에 실패했습니다"로 거절하며, 조인트 구조와 불필요한 조인트도 원인으로 안내한다. 서버가 생성하는 BVH가 이 조건을 만족해야 한다.

### 드래그 구현

`tauri-plugin-drag`로 저장 결과 목록의 각 행을 네이티브 드래그 소스로 만든다.

- 파일은 항상 **복사 모드**로 넘긴다. 드롭 대상이 파일을 가져가도 원본은 저장 폴더에 남아야 한다(`CLAUDE.md` §5 비파괴적 흐름). 실측으로 원본 보존을 확인했다.
- 드롭 결과는 앱이 **모르는 것**만 말한다: "반영됐는지 확인해 주세요". 플러그인이 주는 `Dropped`는 OS 드래그 세션 종료 신호일 뿐 대상 앱의 수용 여부와 무관하므로, "전달됨" 같은 표현과 성공색을 쓰지 않는다(`CLAUDE.md` §10). "놓았습니다"처럼 사용자가 방금 한 동작을 되뇌지도 않는다 — 다인 컷은 행이 여러 개라 행마다 한 문장이 붙으면 목록을 압도한다. 이유는 툴팁으로 내린다.
- 플러그인이 미리보기 이미지 **경로**를 요구하므로, 앱 아이콘을 바이너리에 넣어 두고 앱 데이터 폴더에 한 번 풀어 그 경로를 쓴다(`drag_icon_path` command). 번들 리소스로 두면 개발·배포 경로가 갈리는데 이 방식은 양쪽에서 같다.
- 브라우저 개발 모드에서는 OS 드래그를 시작할 수 없다. `dragService.isSupported`가 false면 드래그 어피던스를 감추고 안내 문구를 폴더 열기 기준으로 바꾼다.
- 드래그 시작이 실패하면 인라인 오류로 폴더 열기를 안내한다.

### 표현 규칙

저장 완료 안내는 "클립스튜디오 캔버스로 끌어놓으세요"까지만 말한다. CSP 내부의 적용 결과를 앱이 알 수 없으므로 "포즈 적용 완료" 같은 단정을 하지 않는다(`CLAUDE.md` §10).

### 폴백

드래그가 동작하지 않는 환경(원격 데스크톱, 일부 태블릿 드라이버)과 구버전 사용자를 위해 세 경로를 남긴다. 드래그가 주 경로여도 이 셋은 유지한다.

- **폴더 열기** → 탐색기에서 CSP 캔버스로 드래그. 팀원이 검증한 경로다
- **경로 복사** → CSP `파일 > 가져오기 > 3D 데이터`의 파일 이름 칸에 붙여넣기
- CSP `파일 > 단축키 설정 > 메뉴 명령`에서 `가져오기 > 3D 데이터`에 단축키를 할당하면 단축키 → Enter → Enter로 줄어든다. 온보딩에서 1회 안내한다.

## 4. 저장 폴더와 파일 이름

### 자동 저장

- 후보를 고르면 즉시 설정된 저장 폴더에 쓴다. 사용자가 폴더나 파일 이름을 확인하는 단계를 두지 않는다.
- 파일 다운로드·쓰기는 ADR-006의 결정대로 Rust command에서 처리한다.
- 같은 이름의 파일이 있으면 덮어쓰지 않고 뒤에 일련번호를 붙인다. 원본을 덮어쓰지 않는 원칙(`CLAUDE.md` §5 비파괴적 흐름)을 저장 결과물에도 적용한다.

### 저장 폴더 규칙

- 최초 기본값: OS 표준 다운로드 폴더
  - Windows: `%USERPROFILE%\Downloads`
  - macOS: `~/Downloads`
  - Tauri의 경로 API로 조회하고 하드코딩하지 않는다.
- **설정 화면에서 변경한다**(`docs/03_USER_FLOW_AND_SCREENS.md` §9 "기본 저장 폴더"). 변경한 경로는 preference로 영속화하고 다음 저장부터 적용한다.
- preference 저장 위치는 앱 데이터 디렉터리(`docs/09_STATE_AND_DATA_MODEL.md` §5 로컬 저장 방식과 동일한 원칙).
- 저장 결과의 **"다른 폴더에 저장"** 버튼은 이번 한 번만 다른 위치에 저장한다. 설정의 기본 폴더는 바꾸지 않는다. 기본 폴더를 바꾸려면 설정 화면으로 간다.
- 선택한 폴더에 쓰기 권한이 없거나 폴더가 삭제된 경우, 저장 시점에 오류를 표시하고 다운로드 폴더로 되돌아가는 옵션을 제공한다.

### 파일 이름

기본 파일명:

```text
standin_pose_YYYYMMDD_HHmm.bvh
```

원본 파일명이 있으면:

```text
{originalName}_standin_pose.bvh
```

다중 인물은 인물별로 파일을 나눈다. 서버가 준 파일명은 신뢰하지 않고 정리하며 확장자는 `.bvh`로 강제한다(ADR-006, `docs/11_QA_SECURITY_RELEASE.md` §3).

## 5. 클립스튜디오 소재 폴더 조사 결과 (종결)

목적: "소재 폴더에 자동 저장해 소재 팔레트에 바로 노출"이 가능한지 판단. **결론은 불가능이며 조사를 종결한다.** 근거를 남겨 다음 작업자가 같은 조사를 반복하지 않게 한다.

### 소재 폴더 위치

- Windows 기본: `Documents\CELSYS\CLIPStudioCommon\Material\` (영문판은 `CELSYS_EN`)
- macOS 기본: `~/Documents/CELSYS/CLIPStudioCommon/` — 일본판 1.6 이상은 실제 데이터를 유저 Library로 옮기고 Documents에 앨리어스만 남기는 경우가 있음
- 사용자가 CLIP STUDIO(런처) → 톱니바퀴 → "소재 저장 장소"에서 임의 경로로 변경할 수 있음. 첫 실행 전에는 폴더 자체가 없음

### 왜 불가능한가

1. **인식 기준이 폴더가 아니라 소재 DB다.** 파일을 폴더에 복사해도 소재 팔레트에 나타나지 않는다. CELSYS 지원 답변 기준으로, 수동 복사 후에는 사용자가 CLIP STUDIO 앱 → 설정 → 메인터넌스 → "소재 데이터베이스 재구성"을 실행해야 한다. 사용자 손이 들어가므로 자동화가 성립하지 않는다.
2. **BVH는 소재 타입이 아니다.** 소재 팔레트의 3D는 `cs3c`/`cs3o`/`cs3s`와 포즈 소재다. BVH는 `파일 > 가져오기 > 3D 데이터` 전용 모션 임포트 포맷이며, DB를 재구성해도 소재로 등재되지 않는다. 이 사실은 CSP 버전과 무관하다.
3. **소재 DB는 미공개 포맷이다.** `%APPDATA%\CELSYS\promenade\dbcache`의 파일은 `CSFCHUNK` 매직으로 시작하는 CELSYS 독자 청크 컨테이너다(`.clip` 파일과 같은 계열). 유효한 항목을 써넣으려면 컨테이너 구조, 소재 카탈로그 스키마, 포즈 페이로드까지 세 겹을 해석해야 한다.
4. **CSP가 소재 쓰기에 프로세스 간 락을 쓴다.** `%APPDATA%\CELSYS\interprocess\`에 `lockInfoMaterialJobInterProcessInfo`, `lockInfoProcessLockWrite`, `OpenManageProcessLockWrite`가 존재한다. 안전하게 쓰려면 CSP 종료가 전제되는데, CSP를 켜둔 채 작업하는 것이 이 앱의 핵심 흐름이라 목적과 충돌한다.
5. **법적으로 안전하지 않다.** CELSYS EULA는 제품의 개조와 리버스 엔지니어링을 포함한 분석을 금지한다. 위 3번 작업이 여기 해당한다. ASSETS에서 받은 소재는 암호화된 구조로 저장되므로, 보호조치를 우회하는 영역까지 가면 저작권법 제104조의2(기술적 보호조치 무력화) 문제가 된다. (법률 자문은 아니다.)

### 리스크 비대칭

기대 이득은 사용자 동작 몇 번 절약이고, 최악 손실은 스키마 오류로 **사용자가 수년간 모은 소재 라이브러리 전체 손상**이다. CSP 업데이트마다 스키마가 바뀌어 깨질 유지비는 그 다음 문제다. 계산이 성립하지 않는다.

## 6. 영구 제외 범위

아래는 재검토 대상이 아니다. 새로 제안될 때마다 §5를 근거로 기각한다.

- **소재 폴더 직접 저장** — §5의 1·2번
- **소재 DB 직접 등재** — §5의 3·4·5번, 리스크 비대칭
- **CSP GUI 키스트로크 자동화** (앱이 CSP 창에 단축키·경로를 전송) — 얻는 것은 키 입력 두 번, 대신 포커스가 어긋나면 캔버스에 경로 문자열이 입력되고, 백신 오탐 대상이며, CSP 버전·언어·DPI마다 다르게 동작한다
- **CSP 오토 액션 활용** — 공식 문서상 도구·서브도구 조작은 레이어와 선택 영역 이동만 기록되고 메뉴·팔레트 조작 중 기록 불가한 항목이 있다. 파일 경로에 의존하는 임포트는 재생이 성립하지 않는다

`CLAUDE.md` §2의 "클립스튜디오 자동 실행" 제외 항목과 같은 결이다.

## 7. 후속 과제

### 후보 카드에서 바로 드래그

지금은 저장이 끝난 뒤 결과 목록에서 드래그한다. 후보 카드 자체를 드래그 소스로 만들면 저장 화면에 들어가지 않고 후보를 고르는 자리에서 바로 넘길 수 있다.

전제 조건: 드래그는 mousedown 시점에 동기적으로 시작되므로 파일이 미리 디스크에 있어야 한다. 즉 후보 표시 시점에 **사전 스테이징**이 필요하다. 인물 5명 × 후보 5개면 요청이 25번이 되므로, 현재 인물 커서의 후보 5개만 스테이징하고 커서 이동 시 추가하는 방식이 맞다.

### FBX 확장

체형 수정이 가능한 3D 모델을 확보한 뒤 FBX 출력을 추가한다. MVP는 BVH만 다룬다.

- FBX는 CSP의 캔버스 드롭 지원 포맷 목록에 공식적으로 포함되어 있고, BVH보다 넓은 버전 범위를 커버한다.
- **제약: CSP의 FBX 지원은 FBX 2014 타입까지다.** 서버에서 익스포트할 때 반드시 2014 이하로 맞추고, 불가하면 OBJ 폴백을 둔다.
- 트레이드오프: FBX는 별도 3D 오브젝트 레이어로 들어오므로 CSP의 관절 UI로 재수정할 수 없다. BVH는 데생 인형에 적용되어 관절 수정이 가능하다. 두 포맷을 병행 출력하고 사용자가 목적에 따라 고르게 한다.

---

## 8. 미결정 / 리스크

- BVH의 캔버스 드롭은 공식 문서의 드롭 지원 포맷 목록에 없는 동작이다. 실측으로는 동작하지만 문서화되지 않은 경로이므로 CSP 버전업에서 바뀔 수 있다. §3 폴백을 유지하는 이유다.
- 드래그가 CSP로 넘어가며 **바가 포커스를 잃을 때** 접히거나 드래그가 취소되지 않는지 아직 확인하지 않았다. 검증은 앱 모드에서 했다(ADR-008 창 구조).
- 서버가 생성할 BVH가 CSP의 조인트 구조 요건을 만족하는지는 별개 문제다. 검증에 쓴 파일은 Mixamo 리그 1프레임이었다.
- BVH 임포트는 CSP Ver 3.1 이상이 필요하다. Ver 1.x 영구 라이선스에 머문 사용자는 이번 범위로 커버되지 않는다. 타깃 사용자층의 CSP 버전 분포를 확인해 FBX 확장 우선순위를 정한다.
- 다중 인물 장면에서 인물별 파일이 여러 개 생긴다. 사용자가 어느 파일이 어느 인물인지 구분할 수 있어야 한다.
- 자동 저장이므로 저장 폴더에 파일이 누적된다. 정리 정책 또는 안내가 필요하다.
- macOS에서 저장 폴더 권한(Documents·Downloads 접근)과 드래그 동작을 Windows와 별개로 확인해야 한다.
