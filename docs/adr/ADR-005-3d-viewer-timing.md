# ADR-005: 3D 뷰어 도입 시점

- 상태: 제안됨
- 날짜: 2026-07-14
- 관련 문서: docs/02_APP_ARCHITECTURE.md §2, docs/03_USER_FLOW_AND_SCREENS.md §7, docs/11_QA_SECURITY_RELEASE.md §6

## 배경

포즈 후보 뷰어는 MVP 핵심이지만, 3D 뷰어를 언제·어떤 형태로 도입할지 미정이다. 서버가 후보를 어떤 형식(렌더 이미지 / GLB / BVH)으로 제공하는지에 종속되며(docs/08 §11 Q8, Q9), 3D 로딩 성능과 리타게팅 불확실성 때문에 Three.js를 앱 전체에 조기 결합하지 않기로 되어 있다(docs/02 §2).

제약:

- 로그인 화면까지 3D 번들을 로드하지 않는다. 3D 뷰어는 lazy load(docs/11 §6).
- 관절 편집은 MVP 제외(docs/03 §7).

## 선택지

### A. 서버 렌더 이미지 기반 뷰어로 MVP 시작 — 권장

- 후보를 정적 다각도 렌더 이미지로 비교(docs/03 §7-1).
- 장점: 가장 빠르고 안정적. 3D 런타임/리타게팅 리스크 없음. 후보 뷰어 흐름(비교·선택·다시 검색)을 3D 없이 완성 가능.
- 단점: 자유 회전 불가. 서버가 뷰 이미지를 제공해야 함(Q8).

### B. GLB 마네킹을 react-three-fiber로 렌더

- 장점: 회전/확대 등 인터랙션.
- 단점: 서버가 GLB 제공 필요. 로딩 성능·번들 크기 관리 부담.

### C. BVH를 기준 리그에 적용한 Three.js 뷰어

- 장점: 실제 포즈를 3D로 확인.
- 단점: 리타게팅 난도 높고 불확실. MVP엔 과함.

## 결정

**A. 서버 렌더 이미지 기반**으로 MVP를 시작한다. 3D(B/C)는 서버 형식이 확정된 뒤 lazy-load 모듈로 도입한다.

근거:

- 후보 뷰어의 사용자 가치(5개 비교·선택·다시 검색)는 이미지만으로 충족된다.
- 3D를 앱 셸에 결합하지 않으면 성능/번들 리스크를 미루고, 서버 협의 결과에 맞춰 안전하게 확장할 수 있다.

## 결과

- 뷰어 컴포넌트는 "후보 표현 방식"을 추상화해 이미지 뷰어를 먼저 구현하고, 3D 뷰어를 나중에 같은 자리에 끼울 수 있게 인터페이스를 둔다.
- 3D 도입 시 `pose-viewer` feature 내부에서 `React.lazy`로 분리해 초기 로드에 영향 없게 한다(docs/11 §6).
- 서버팀 확인(docs/08 §11 Q8, Q9): 후보 렌더 이미지 제공 여부, BVH 사전 생성 여부.
- 재검토 조건: 서버가 GLB/BVH + 기준 캐릭터를 제공하고 회전 뷰 요구가 확인되면 B를 별도 ADR로 도입.
