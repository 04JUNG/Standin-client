# 요청: 조정본(refined) 썸네일 렌더 — 추론 서버

> 보내는 쪽: Standin Desktop(클라이언트) + Standin BFF
> 받는 쪽: Standin-server(추론, 도원)
> 관련: `docs/adr/ADR-010-refine-review-step.md`, `Standin-server/docs/REFINE_DESIGN.md`

> **상태: 처리됨 (2026-09-04).** 추론이 §3의 **(a) 인라인 data**로 구현했다
> (Standin-server `feat(refine): return front thumbnail preview`, develop). 요청과 다른 점 둘:
> `view`는 front 고정이 아니라 **선택한 후보의 view를 유지**하고, `refined=false`일 때도
> 썸네일을 준다 — 기존 베이스 썸네일 파일이 아니라 **실제로 저장될 베이스 BVH를 같은
> 렌더러로 새로 렌더한 것**이라 §3 요건("refined=false면 썸네일도 없어야 한다")보다 낫다.
> BFF·클라이언트 대응은 ADR-010 개정 2를 본다. 아래 §5는 더 이상 유효하지 않다.
>
> ⚠ 남은 어긋남: 렌더 실패가 `409 refine_thumbnail_failed`로 `/refine` **전체를 실패시킨다.**
> §3 요건("렌더 실패는 오류가 아니다")과 반대다. BFF가 이 409를 `upstream_unavailable` 스킵으로
> 흡수하므로 저장은 막히지 않지만, 그림을 못 그렸다는 이유로 조정 결과까지 버려진다.

## 1. 무엇이 없는가

저장 전 확인 화면(ADR-010)은 "무엇이 저장되는지"를 보여줘야 한다. 지금은 인물·후보 이름만
목록으로 보여준다. 후보 화면은 추론이 렌더한 PNG 썸네일(`GET /pose/{id}/thumbnail?view=`)을
쓰지만, **조정본에는 대응하는 썸네일이 없다.** 조정본은 라이브러리에 없는 새 포즈이기 때문이다.

그래서 지금 화면은 이렇게 된다.

```text
후보 선택 화면   → 후보 썸네일(추론 렌더)  ← 사용자가 보고 고른 그림
저장 전 확인 화면 → 이름 목록               ← 실제로 저장될 포즈는 조정본
```

사용자는 자기가 고른 그림을 보고 확정하지만, 저장되는 것은 그 그림이 아니다.

## 2. 왜 클라이언트에서 그리지 않는가

한 번 시도했고 되돌렸다(`a31aeda`, 2026-08-05). BVH를 three.js로 그렸더니 실제 자세가 아니라
기본 T자 뼈대가 나왔다 — 저장될 포즈라며 틀린 자세를 보여주는 상태라, 확인 수단이 없는 것보다
나빴다. 번들도 373 kB → 895 kB로 늘었다.

기술적으로 고칠 수 있는 버그이지만(첫 MOTION 프레임을 적용하지 않은 문제로 보인다), 고쳐도
남는 문제가 둘이다.

1. **시각 언어가 다르다.** 후보는 렌더된 캐릭터, 확인 화면은 막대 스켈레톤이 된다. 같은 포즈를
   두 가지로 그려 놓고 "같은 것"이라고 믿게 만드는 화면이 된다.
2. **최종 산출물과 다르다.** 제품 export는 이제 V3.2 retarget FBX다. retarget은 ankle/pelvis
   freeze 정책을 적용하므로 원본 BVH와 최종 FBX가 정확히 같지 않다. 클라이언트가 BVH를 그리면
   "저장될 것"이 아니라 "저장될 것과 비슷한 것"을 보여주게 된다.

추론이 이미 후보 썸네일을 렌더하고 있으므로, 같은 렌더러로 조정본을 한 장 더 그리는 것이
두 문제를 동시에 없앤다.

## 3. 요청 내용

`POST /refine` 응답에 조정본 썸네일을 추가한다. 형태는 둘 중 하나면 된다.

**(a) 응답에 inline data URI** — 라운드트립이 늘지 않는다. 조정본 BVH를 이미 inline으로 싣고
있으므로 같은 성격이다.

```json
{
  "refined": true,
  "bvh": "HIERARCHY\n...",
  "thumbnail": "data:image/png;base64,...",
  "thumbnail_view": "front"
}
```

**(b) 짧은 수명의 조회 경로** — 응답 크기를 키우지 않는다. 다만 조정본은 태스크 로컬 디스크에
두지 않기로 이미 정했으므로(`REFINE_HANDOFF` §3 4단계에서 `/refined/{handle}/bvh` 제거),
경로를 다시 만들려면 그 결정을 뒤집지 않는 저장 위치가 필요하다. **(a)를 선호한다.**

### 요건

- 후보 썸네일과 **같은 렌더러·같은 카메라·같은 뷰**. 나란히 놓고 비교하는 화면이라 두 그림의
  조건이 다르면 조정 결과가 아니라 렌더 차이를 보게 된다.
- `refined=false`면 썸네일도 없어야 한다(베이스 후보의 기존 썸네일을 그대로 쓴다).
- 크기는 후보 썸네일과 같은 수준이면 충분하다. 확인 화면은 인물당 한 장만 쓴다.
- 렌더 실패는 **오류가 아니다.** refine 자체와 마찬가지로 "썸네일 없음"으로 정상 응답한다 —
  그림을 못 그렸다고 저장이 막히면 안 된다.

### 선택: 최종 FBX 기준 렌더

가장 정확한 그림은 converter가 만든 FBX를 렌더한 것이다. 다만 인물당 변환이 3초대이므로
확인 화면에서 동기로 기다리게 하기는 어렵다. 조정본 BVH 기준 썸네일이면 현재 필요를 충족한다.
FBX 기준 렌더는 converter latency가 ECS에서 측정된 뒤에 다시 판단한다.

## 4. 받는 쪽에서 이어질 작업

| 저장소 | 작업 |
|---|---|
| Standin-server | `/refine` 응답에 썸네일 추가 |
| Standin-app-server(BFF) | refine 응답의 썸네일을 클라 refine 응답으로 통과. 조정본과 함께 보관 |
| Standin Desktop | 확인 화면에서 인물별 조정본 썸네일 표시 |

BFF는 조정본 BVH를 이미 S3에 보관하므로 썸네일도 같은 키 공간에 넣으면 재진입(작업 기록에서
다시 열기)에서도 같은 그림이 나온다.

## 5. 그때까지

확인 화면은 지금처럼 인물·후보 이름 목록을 유지한다. 틀린 그림을 보여주는 것보다 낫다는
`a31aeda`의 판단은 유효하다.
