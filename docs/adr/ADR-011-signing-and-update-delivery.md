# ADR-011: 데스크톱 앱 서명과 자동 업데이트 배포 방식

- 상태: 제안됨
- 날짜: 2026-08-26
- 관련 문서: docs/11_QA_SECURITY_RELEASE.md §7, docs/05_REPOSITORY_AND_COLLABORATION.md, CLAUDE.md §10, .github/workflows/release-desktop.yml

## 배경

현재 릴리스는 서명 없이 나간다. `release-desktop.yml`이 main에서 수동 실행되어 Windows NSIS 설치 파일과 macOS dmg(aarch64·x86_64) 세 개를 GitHub Releases에 올리는 것이 전부다. 이 상태에서 두 가지가 막혀 있다.

**설치 자체가 막힌다.** macOS는 공증(notarization)되지 않은 dmg를 Gatekeeper가 차단한다. 테스터가 우클릭 열기나 `xattr` 제거를 직접 해야 하는데, 이건 대상 사용자(웹툰 작가)에게 요구할 수 있는 동작이 아니다. Windows는 설치는 되지만 SmartScreen이 "알 수 없는 게시자"로 경고한다.

**업데이트 경로가 없다.** 클로즈베타는 수정 회전이 빠른데(0.1.1-beta.2까지 오는 동안 핫픽스가 여러 번 나갔다) 매번 테스터가 수동으로 내려받아 재설치해야 한다. 버전이 갈리면 어떤 빌드에서 난 문제인지 추적도 어렵다.

자격증명은 확보됐다. Apple Developer Program 가입, SSL.com IV(Individual Validation) 코드서명 인증서 구매를 마쳤다. 이제 정할 것은 그것을 **어디서 어떻게 쓰고, 업데이트를 어디로 배포하느냐**다.

결정 전에 짚어야 할 제약이 셋 있다.

- **서명은 두 종류이고 서로 무관하다.** OS 코드서명(Apple Developer ID / SSL.com)은 설치 시 경고를 없앤다. Tauri 업데이터 서명(minisign 키쌍)은 업데이트 패키지의 위변조를 막는다. 둘 다 필요하고 대체 관계가 아니다.
- **이 둘의 되돌리기 비용이 비대칭이다.** OS 인증서는 만료·재발급해도 자동 업데이트가 깨지지 않는다. 반면 **업데이터 minisign 개인키를 잃으면 이미 배포된 앱은 영구히 자동 업데이트를 받지 못한다.** 새 설치 파일을 배포해 갈아끼우는 것 외에 복구 수단이 없다. ADR로 남기는 핵심 이유가 이 비대칭이다.
- **IV 인증서는 SmartScreen을 즉시 없애주지 않는다.** 2023년 이후 코드서명 인증서는 종류와 무관하게 FIPS 하드웨어 보관이 의무이고, SmartScreen 평판이 즉시 부여되는 것은 EV뿐이다. IV/OV는 다운로드 수가 쌓이며 평판이 축적된다. 서명하면 게시자가 실명으로 바뀌지만 초기에는 경고가 남을 수 있다.

## 선택지

결정할 축이 셋이다.

### 축 1. 업데이트 배포 채널

- **A. GitHub Releases 정적 `latest.json`.** `releases/latest/download/latest.json`을 엔드포인트로 쓴다. 릴리스 워크플로가 파일을 생성해 함께 올리므로 추가 인프라가 없다. 단 GitHub의 `/releases/latest`는 prerelease를 잡지 않으므로 현재 `prerelease: true` 설정과 양립하지 않는다. 배포 대상을 고르거나 되돌릴 수단이 없어 올리는 순간 전원에게 나간다.
- **B. 자체 서버(BFF) 동적 엔드포인트.** `api.standinpose.com`에 `{{target}}`·`{{arch}}`·`{{current_version}}`을 받는 라우트를 두고 업데이트가 없으면 204를 반환한다. 대상 제어·롤백·업데이트 적용 수 집계가 가능하다. 대신 다른 저장소(`Standin-app-server`) 작업이 병행되고, 서버 장애가 곧 업데이트 중단이 된다.
- **C. 업데이터 없음.** 수동 재설치를 계속 안내한다. 작업이 0이지만 문제가 그대로 남는다.

### 축 2. macOS 빌드 타깃

- **D. 아키텍처별 dmg 2개(현행).** 공증을 빌드마다 따로 거쳐야 하고, `latest.json`에 `darwin-aarch64`·`darwin-x86_64` 항목을 각각 관리한다. 사용자가 자기 맥의 칩을 알아야 한다.
- **E. universal 단일 빌드.** 공증 1회, 릴리스 자산 1개, `latest.json` 항목 1개. 바이너리에 두 아키텍처가 들어가 용량이 늘어난다.

### 축 3. Windows 서명 수행 위치

- **F. SSL.com eSigner 클라우드 서명.** CI에서 `bundle.windows.signCommand`로 CodeSignTool을 호출한다. 릴리스가 자동화 안에 남는다. 클라우드 호출이라 파일당 지연이 있고 서명 횟수 쿼터의 영향을 받는다.
- **G. YubiKey 하드웨어 토큰.** 담당자 PC에서 수동 서명한다. 쿼터·네트워크 영향이 없지만 릴리스가 특정 사람과 특정 기계에 묶이고, CI에서 나온 산출물을 손으로 옮겨 서명하는 단계가 생긴다.

## 결정

**A + E + F를 택한다. A는 B로 승격할 수 있는 형태로 만든다.**

근거:

- **채널은 A로 시작한다.** 서명과 공증은 처음 붙일 때 실패 왕복이 잦은 작업이다. 여기에 새 서버 라우트를 동시에 넣으면 "업데이트가 안 뜬다"의 원인이 서명인지 엔드포인트인지 분리되지 않는다. 클로즈베타 규모에서 B의 이득(대상 제어·롤백)은 아직 가정이고, 잘못된 버전을 실제로 내보내 본 뒤에 도입해도 늦지 않다.
- **A를 고르는 것이 B를 막지 않는다.** Tauri 업데이터의 `endpoints`는 배열이고 앞에서부터 시도한다. BFF URL을 배열 앞에 끼워 넣으면 승격이 끝나고, 그때 GitHub 경로는 폴백으로 남는다. 되돌리기 비용이 작은 쪽을 먼저 하는 것이 순서에 맞다.
- **A를 성립시키기 위해 GitHub Release의 `prerelease` 플래그를 끈다.** 버전 문자열의 `-beta.N`이 이미 베타 표기를 담당하므로 플래그가 중복이고, 플래그를 유지하면 `releases/latest/...` 경로 자체가 잡히지 않는다.
- **macOS는 E로 통합한다.** 공증은 Apple 서버 대기가 포함되어 실패 시 왕복 비용이 큰 단계인데, 현행 D는 그 비용을 빌드마다 두 번 낸다. 사용자가 "내 맥이 어느 칩인가"를 판단해야 하는 것도 클로즈베타 테스터에게는 실제 마찰이다. 늘어나는 용량은 Tauri가 WebView를 시스템에서 가져오므로 증가분이 작고, 의존 크레이트(`xcap`·`keyring`·`tauri-plugin-drag`)가 모두 순수 Rust라 두 아키텍처 빌드에 걸리는 것이 없다.
- **Windows는 F로 한다.** G는 릴리스를 사람과 기계에 묶는다. 지금도 릴리스가 수동 실행이라 병목이 있는데, 여기에 "특정 PC에 토큰을 꽂아야 함"을 더하면 담당자 부재 시 핫픽스가 나가지 못한다. F의 약점(쿼터·지연)은 릴리스 빈도가 낮아 감당 가능한 범위이고, 한계에 부딪히면 G로 폴백할 수 있다.
- **업데이터 minisign 키쌍은 채널과 무관하게 하나만 유지한다.** 채널을 A에서 B로 바꿔도 키는 그대로다. 채널 변경이 키 교체를 유발하지 않도록 분리하는 것이 승격 경로를 싸게 만든다.

## 결과

### 후속 작업

- **자격증명 준비는 릴리스 담당자가 직접 수행한다.** 인증서 발급, `.p12` 추출, GitHub Secrets 등록은 비밀정보를 다루므로 자동화 대상이 아니다. 필요한 Secrets 이름 목록은 구현 시점에 README에 정리한다(값은 문서에 남기지 않는다, CLAUDE.md §10).
- 순서는 **macOS 서명·공증 → Windows 서명 → 업데이터 배선**이다. macOS 업데이터는 갱신된 앱이 Gatekeeper를 통과해야 재실행되므로 서명이 선행 조건이다.
- `bundle.createUpdaterArtifacts`를 켜고 `plugins.updater`에 공개키와 엔드포인트를 넣는다. 공개키는 저장소에 커밋하고, 개인키는 GitHub Secrets와 **오프라인 백업 두 곳**에 둔다.
- `capabilities/default.json`에 `updater:default`와 재시작에 필요한 권한만 추가한다. 최소 capability 원칙(docs/11 §3)에 따라 `process:default`처럼 넓은 묶음을 쓰지 않는다.
- 설정 화면에 **현재 버전 표시와 업데이트 확인 섹션**을 만든다. 지금 앱에는 버전을 확인할 곳이 아예 없어서 테스터가 어떤 빌드를 쓰는지 스스로 말할 수 없다.
- **분석 Job이 진행 중일 때는 재시작을 유도하지 않는다.** 처리 중인 작업의 상태를 알 수 있어야 한다는 원칙(docs/11 §1)이 업데이트 재시작에도 적용된다.
- 공개키와 엔드포인트가 설정되기 전에는 업데이트 확인 UI를 노출하지 않는다. 동작하지 않는 기능을 동작하는 것처럼 보이게 하지 않는다(CLAUDE.md §10).
- dev 빌드(`ci.yml`의 develop 푸시 빌드)는 **서명하지 않는다.** macOS는 현행 ad-hoc 서명(`signingIdentity: "-"`)을 유지한다. 서명 쿼터와 빌드 시간을 릴리스에만 쓴다.
- docs/11 §7의 릴리스 체크에서 "signing 설정", "자동 업데이트는 준비되기 전 비활성" 항목을 이 결정에 맞게 갱신한다.
- 세부 절차 문서(설치 방법, Secrets 목록, 서명 래퍼 스크립트 사용법)는 **Windows 서명까지 실제로 성공한 뒤에 쓴다.** 실행 전에 쓰면 절반이 추측이 되고, 이 저장소는 문서 우선순위가 높아 틀린 문서의 비용이 크다.

### 감수하는 트레이드오프

- **초기 Windows SmartScreen 경고가 남을 수 있다.** IV 인증서는 평판 축적형이다. 릴리스 노트와 다운로드 안내에 이 기대치를 적고, 경고 화면에서 진행하는 방법을 안내한다.
- **A안에서는 배포 대상을 고를 수 없다.** 올리는 순간 모든 사용자에게 나간다. 잘못된 릴리스는 상위 버전을 다시 올려 덮는 것이 유일한 대응이다.
- **eSigner 클라우드 서명이 릴리스를 외부 서비스에 의존시킨다.** SSL.com 장애 시 서명된 릴리스를 만들 수 없다.
- **universal 빌드는 두 아키텍처를 모두 담아 용량이 늘어난다.** 다운로드 크기보다 공증 왕복 횟수와 사용자 혼란을 줄이는 쪽을 택했다.

### 재검토 조건

- 사용자 수가 늘거나 잘못된 버전을 실제로 내보내 회수가 필요해지면 **B(BFF 엔드포인트)로 승격**한다. `endpoints` 배열 앞에 추가하는 작업이다.
- eSigner 서명 횟수 쿼터나 빌드 지연이 릴리스를 막으면 **G(하드웨어 토큰 수동 서명)로 폴백**한다.
- 정식 출시 시점에 SmartScreen 경고가 여전히 문제가 되면 **EV 인증서 전환**을 검토한다. 업데이터 키와 무관하므로 전환 비용은 워크플로 수정에 그친다.
- Apple Developer ID 인증서와 SSL.com 인증서의 만료일을 릴리스 체크에 포함하고, 만료 전에 재발급한다. 재발급은 자동 업데이트에 영향을 주지 않는다.
