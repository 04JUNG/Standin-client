# ADR-008: 플로팅 바의 창 구조

- 상태: 제안됨
- 날짜: 2026-07-28
- 관련 문서: docs/03_USER_FLOW_AND_SCREENS.md, docs/07_CAPTURE_AND_UPLOAD_SPEC.md, docs/09_STATE_AND_DATA_MODEL.md, ADR-002, ADR-003

## 배경

작가는 클립스튜디오로 그리다가 포즈를 찾는다. 지금 구조에서는 캡처하려면 Standin 앱 창으로 전환해야 하고, 후보를 비교하려면 앱 창에 머물러야 한다. 그림 작업 흐름이 매번 끊긴다.

요구: **앱 창에 진입하지 않고** 작업 화면 위에서 캡처·업로드하고, 포즈 후보를 확인하고, 저장까지 끝낸다. 옮길 수 있는 항상-위 버튼을 두고 단축키나 그 버튼으로 바를 펼친다.

이 개념은 기존 명세에 없다. 오히려 `docs/03`·`docs/07`·ADR-003은 캡처 후 **"앱 복귀"**를 전제로 쓰여 있어 함께 정정해야 한다.

제약:

- 인증 토큰은 `client.ts`의 모듈 메모리에 있고 refresh 토큰도 인메모리다(ADR-002가 보안 저장소 도입을 후속으로 미뤄둔 상태).
- Zustand 스토어와 TanStack Query 캐시는 JS 컨텍스트에 종속된다.
- 최소 capability 원칙(docs/11 §3).
- 캡처는 메인 창을 숨겼다가 되살리는 기존 흐름을 그대로 써야 한다(ADR-003).

## 선택지

### A. 기존 `main` 창 하나를 모드 전환한다 (권장)

창 하나를 바(작고 항상 위·테두리 없음) ↔ 앱(1280×800) ↔ 오버레이(전체화면)로 변형한다.

- 장점: **JS 컨텍스트가 하나라 기존 인증·스토어·Query가 무수정으로 동작한다.** 이것이 결정적이다.
- 장점: 창 조작 command 하나로 끝나 capability 추가가 없다.
- 단점: 바와 전체 앱 화면을 동시에 볼 수 없다.

### B. 둘째 창을 만들고 메인 창이 상태를 소유한다

오버레이 전용 창을 띄우고, 숨긴 메인 창이 인증·API·상태를 전부 소유한다. 바는 Tauri 이벤트로 의도만 보내고 밀려받은 상태만 그린다.

- 장점: 바와 앱 화면을 동시에 볼 수 있다.
- 단점: **창 간 상태 동기화 계열을 새로 지어야 한다.** 후보 목록·진행 상태·저장 결과를 전부 이벤트로 미러링해야 하고, 두 컨텍스트가 어긋날 때의 복구 규칙까지 설계 대상이 된다.
- 단점: 창 생성·표시에 `core:window` 권한이 필요하고 새 창 label을 capability에 추가해야 한다.

### C. 둘째 창 + 토큰을 Rust로 이전

둘째 창이 자체적으로 API를 호출하도록 토큰을 Rust 보안 저장소로 옮긴다(ADR-002의 TODO를 함께 소화).

- 장점: 가장 유연하다. 창을 더 늘려도 구조가 버틴다.
- 단점: 인증 재설계가 선행되어야 해 범위가 가장 크다. 이번 기능과 인증 변경을 한 브랜치에 묶으면 되돌리기 어렵다.

## 결정

**A**를 택한다.

B와 C의 공통 장점인 "동시 표시"는 지금 요구에 없다. 요구는 "앱에 **진입할 필요가 없게**"이지 "둘을 같이 보게"가 아니다. 반면 B·C가 치러야 하는 비용(창 간 상태 동기화, 인증 재설계)은 즉시 실재한다.

## 결과

- 모드는 `bar` · `app` · `overlay` 셋이고 `set_window_mode` command가 원자적으로 전환한다. 개별 창 조작을 JS에서 조합하면 중간 실패 시 반쯤 전환된 창이 남는다.
- **전환 순서가 함정이다.** 바·오버레이로 갈 때 `set_min_size(None)`을 먼저 호출해야 한다. `tauri.conf.json`의 `minWidth`/`minHeight`(960×640) 때문에 그냥 줄이면 56×56이 거부된다. 앱 복귀 시에는 크기를 키운 뒤 최소 크기를 복원한다.
- **capability가 하나 줄었다.** 전체화면 전환이 JS에서 Rust로 옮겨가 `core:window:allow-set-fullscreen`이 불필요해졌다. 남은 권한은 `core:default` · `opener:default` · `deep-link:default` 셋뿐이다.
- **모드의 진실 공급원은 라우트 하나다.** `WindowModeSync`가 `useLocation`에서 모드와 크기를 파생해 반영하므로 창 상태와 화면 내용이 어긋날 수 없다. 이를 위해 pathless 레이아웃 라우트를 도입했다(기존 flat 라우터에는 앱 전역 마운트 지점이 없었다).
- 바 위치는 영속화하고 `current_monitor()`의 작업 영역으로 클램프한다. 사라진 모니터를 가리키거나 해상도가 바뀌어도 바가 화면 밖으로 나가지 않는다.
- 흐름 분기는 `origin`(`app` | `bar`) 하나로 처리한다. 진입 시점에 기록하고 `flowOrigin`이 목적지를 계산하므로 각 단계가 개별 분기하지 않는다.
- 앱/바 두 뷰는 `useAnalysisResult` · `useSaveFlow`로 로직을 공유한다. 뷰만 두 벌이고 오케스트레이션은 한 벌이다.
- 전역 단축키 목적지가 "즉시 캡처"에서 "바 열기"로 바뀐다. 바가 펼쳐져 있으면 접는 토글이고, 흐름 도중에는 작업을 잃지 않도록 접지 않는다.
- ~~바를 투명 배경으로 만들지 않는다.~~ → **번복함(아래 실측 보정 참고).**
- **ADR-003 정정**: "투명 오버레이 창"으로 적혀 있으나 실제 구현은 메인 창의 라우트다. 이 ADR이 그 구조를 확정한다.
- 재검토 조건:
  - 바와 전체 앱 화면을 **동시에** 봐야 하는 요구가 생기면 B/C로 전환한다. 그때는 인증 토큰의 Rust 이전(ADR-002)이 선행되어야 한다.
  - 바에서 다뤄야 할 인물 수가 스테퍼로 감당이 안 되면 후보 패널 레이아웃을 다시 본다.

## 실측 보정 (2026-07-28, Windows 11)

접힌 바가 "흰 네모 안의 동그란 버튼"으로 보인다는 보고를 받고 Win32로 창 속성을 측정한 결과, 위 결정 중 창 장식 관련 부분을 세 가지 바로잡았다.

### 1. 런타임 `set_decorations(false)`가 동작하지 않는다

바 모드로 전환해도 `WS_BORDER`·`WS_DLGFRAME`이 그대로 남아 프레임이 그려졌다. 호출 순서를 바꿔도(장식 해제를 마지막에), 창을 무장식으로 생성해도 결과가 같았다. 반면 `set_decorations(true)`는 정상 적용된다.

→ **모드마다 장식을 토글하는 방식을 포기했다.** 창을 항상 무장식으로 두고 앱 모드는 제목 표시줄을 직접 그린다(`app/AppTitleBar.tsx` + `window_control` command). 창 제어도 자체 command라 capability가 늘지 않는다.

### 2. `shadow: false`가 흰 네모의 실제 원인이었다

투명 창으로 바꾼 뒤에도 둥근 흰 판이 남았다. Tauri 문서대로 Windows에서 `shadow: true`인 무장식 창은 **1px 흰 테두리와 둥근 모서리**를 얻는다 — 보고된 증상과 정확히 일치한다. `shadow: false`로 두자 창 여백이 (0,0)이 되어 클라이언트 영역과 창이 정확히 같아졌고 네모가 사라졌다.

→ `transparent: true` + `decorations: false` + `shadow: false` 세 개가 함께 있어야 한다. 바 모드에서는 `body` 배경도 비운다(`body[data-window-mode="bar"]`).

macOS는 `transparent`에 `macos-private-api`가 필요하다. 이 저장소는 Windows 우선이고 macOS는 이미 전 범위 미검증이므로 그대로 두되, macOS 지원 시 함께 판단한다.

### 3. 최대화 상태에서는 `set_size`가 무시된다

사용자가 앱 창을 최대화해 두면 바로 전환해도 크기가 그대로였다. Windows가 최대화 창의 `set_size`를 무시하기 때문이다. 바·오버레이 전환 시 `unmaximize()`를 먼저 호출한다. 반대로 앱 모드로 돌아올 때는 최대화를 존중해 크기를 되돌리지 않는다 — 앱 화면 사이를 오갈 때마다 사용자가 정한 크기를 빼앗지 않기 위해서다.

### 곁들여: 접힌 버튼은 클릭과 끌기를 겸해야 한다

`data-tauri-drag-region`은 mousedown에서 `preventDefault` 후 바로 끌기를 시작해 클릭을 삼킨다. 그래서 접힌 버튼에는 쓸 수 없고, 포인터가 4px 넘게 움직인 뒤에만 `startDragging`을 호출하는 `useDragOrClick`으로 처리한다. 제자리 클릭은 펼치기, 끌면 이동이다.

## 보완 (2026-07-31): 모드를 바꿔도 단계를 유지한다

"바에서 후보를 고르다 앱 창으로 바꾸면 첫 화면이 된다"는 보고를 받았다.

흐름 상태 자체는 이미 공유되고 있었다 — 창이 하나라 Zustand 스토어와 Query 캐시가 그대로 살아 있다(선택 A의 핵심 장점). 잃던 것은 **어디까지 왔는지**뿐이었고, 원인은 전환 버튼들이 목적지를 고정해 둔 것이었다.

- 바의 확대 버튼 → 항상 `/app/home`
- 앱 상단의 `플로팅 바` 버튼 → 항상 `/bar/actions`
- 최소화 가로채기 → 앱에서는 항상 접힌 `/bar`

→ 두 방향의 대응표를 `shared/lib/modeRoutes.ts` 하나로 모은다. `/bar/candidates` ↔ `/app/jobs/:jobId`, `/bar/save` ↔ `/app/jobs/:jobId/save`, `/app/preview` → `/bar/actions`. jobId와 초안 유무는 호출부가 스토어에서 읽어 넘기므로 이 모듈은 순수 함수로 남고 왕복 불변식을 테스트로 고정한다.

바 셸과 앱 셸이 함께 쓰므로 `features/bar`가 아니라 `shared`에 둔다(shared는 features를 import하지 않는다).

최소화도 바뀌었다. 종전에는 흐름 도중 앱 창에서 최소화하면 접힌 바로 가서 흐름 위치를 잃었고, 바 안에서는 아무 일도 하지 않았다. 이제 앱 창에서는 같은 단계의 바 화면으로 접고, 바 안에서 흐름 중일 때는 종전대로 접지 않는다.

### 곁들여: 좁은 바에는 작은 버튼 크기가 필요하다

420px 저장 패널에서 `다른 폴더`가 두 줄로 깨졌다. 아이콘 + 라벨 + 3키 단축키 칩(`Ctrl Shift O`)이 절반 폭 버튼에 들어가지 않았기 때문이다. 단축키 표시는 요구사항이므로(docs/04 §13) 지우지 않고 `Button`에 `sm` 크기와 `ShortcutKey`에 `compact`(18px 칩)를 더했다. 라벨은 `whitespace-nowrap`으로 두어 폭이 모자라면 줄바꿈 대신 부족분이 드러나게 한다 — 줄바꿈은 깨진 것처럼 보이고 원인도 감춘다.

## 구현 정정 (2026-08-28, macOS 오버레이는 네이티브 전체화면을 쓰지 않는다)

0.1.1-beta.4에서 **캡처를 마치면 앱이 화면 전체를 검게 덮고 그 안에 바가 떠 있는** 상태가 보고됐다. 무장식이어야 할 창에 제목 표시줄까지 되살아났다.

원인은 macOS의 전체화면이 **비동기**라는 점이다. tao는 `toggleFullScreen:`을 async로 부르고, 전환 중에 들어온 요청은 전환이 끝난 뒤로 미룬다(`in_fullscreen_transition`). 그래서 오버레이를 빠져나오는 순서가 이렇게 깨진다.

```text
set_fullscreen(false)   → 전환 시작(애니메이션)
set_resizable(false)    → 전환 중이라 스타일 마스크 변경이 보류됨
set_size(360×64)        → 적용되지만
(전환 완료)             → 창 프레임이 전체화면 크기로 되돌아감
```

Windows에는 이 문제가 없다. 전체화면 전환이 동기다.

결정:

- **macOS에서는 오버레이에 네이티브 전체화면을 쓰지 않는다.** 덮을 모니터의 좌표·크기로 창을 직접 맞춘다. 전부 동기라 전환 창(window)이 존재하지 않는다. 어차피 오버레이가 덮을 모니터는 캡처한 쪽이 이미 알려주므로(ADR-003) 새로 필요한 정보가 없다.
- Windows는 기존 경로를 유지한다. 동작하는 것을 굳이 바꾸지 않는다.
- 잃는 것: 메뉴 막대와 Dock이 오버레이 위에 남는다. 전체화면일 때도 메뉴 막대는 보였고, 바가 깨지는 것보다 낫다. 창 레벨을 올려 덮는 방법은 macOS 전용 코드가 더 필요하므로 후속으로 둔다.

## 구현 정정 (2026-08-28, 바 창은 내용에 맞춰 커진다)

0.1.1-beta.5 드래프트에서 **권한이 꺼진 채 바의 캡처 버튼을 눌러도 아무 반응이 없다**고 보고됐다. 같은 조작을 앱 창에서 하면 안내가 정상적으로 떴다.

오류는 정상적으로 렌더되고 있었다. 바 창이 `/bar/actions`에서 **360×88 고정**이고 그 높이는 헤더와 버튼 한 줄에 딱 맞춰져 있어, 그 아래 붙는 오류 안내가 창 밖으로 잘렸을 뿐이다. 사용자에게는 "버튼이 죽은" 것으로 보인다.

크기 표(`BAR_SIZES`)는 평상시 높이만 담는다. 오류 안내처럼 **그때만 생기는 줄**을 표에 미리 넣을 수는 없다. 같은 함정이 업로드 실패 문구에도 이미 있었다.

결정:

- `BarShell`이 **내용 자체의 높이**를 재서 store에 올리고, 창에 적용하는 곳은 여전히 `WindowModeSync` 하나다. 크기를 쓰는 곳이 둘이 되면 서로 덮어쓴다.
- 창은 표 높이보다 작아지지 않는다(`max(표, 측정값)`). 표는 하한이고 측정값은 넘칠 때만 쓰인다.
- 측정 대상은 **창 크기와 무관해야 한다.** 스크롤 영역의 높이는 창을 따라가므로, 그것으로 계산하면 키움 → 재측정 → 줄임이 반복된다. 그래서 스크롤 영역이 아니라 그 안의 내용 래퍼를 잰다. 브라우저에서 확인한 값: 평상시 87(표 88이 이김), 오류 한 줄이 붙으면 139.
